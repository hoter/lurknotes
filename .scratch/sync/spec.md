# LurkNotes — синхронизация с сайтом: спека

Версия 0.1. Дата: 2026-11-21. Статус: черновик для реализации.

Спека собрана из закрытых тикетов карты [`.scratch/sync/`](map.md): решения
01–04 и 08–09, отчёты [research 05](research/05-laravel-storage.md) и
[research 06](research/06-client-http-queue.md). Термины — в
[GLOSSARY.md](../../GLOSSARY.md).

Документ описывает **две стороны**: клиент (GitHub `hoter/lurknotes`, Python +
GTK 4) и сервер (GitLab `hoter/lurknotes`, Laravel 13). По этой спеке можно
написать обе, не переспрашивая.

---

## 1. Что это

Пользователь может **по выбору** синхронизировать колоду заметок между
машинами через сайт LurkNotes. По умолчанию синхронизация выключена, и
приложение ведёт себя точно как описано в [спеке v1](../edge-notes/spec.md):
всё локально, ни одного сетевого запроса.

Включённая синхронизация — двусторонняя: правки на любой машине появляются
на остальных, и то же видно на сайте. Замечания сводятся к одному правилу:
**побеждает последняя запись**, измеренная серверным временем. Конфликтные
копии не создаются.

### 1.1 Границы

- У одного пользователя один **Vault** — набор его заметок на сервере.
- Заметка принадлежит одному пользователю; общих заметок нет.
- Сайт показывает список заметок и одну заметку на чтение и правку.
- Мобильных приложений нет.

## 2. Термины

Полный список — в глоссарии. Здесь только те, что используются ниже и
специфичны для синхронизации.

| Термин | Значение |
|---|---|
| **Vault** | Колода пользователя на сервере; одна на аккаунт. |
| **Очередь (queue)** | Список ещё не отправленных изменений в `queue.json` на клиенте. |
| **Tombstone** | Запись о том, что заметка удалена; живёт на сервере 30 дней. |
| **`server_updated_at`** | Серверная метка версии заметки. Единственное время, участвующее в разрешении конфликтов. |
| **Курсор синхронизации** | Момент, до которого клиент уже получил изменения; хранится в `sync.json`. |

## 3. Модель данных

### 3.1 Заметка на сервере

| Поле | Тип | Описание |
|---|---|---|
| `id` | bigint, PK | Внутренний идентификатор строки. |
| `user_id` | FK `users.id` | Владелец; каскадное удаление с пользователем. |
| `client_id` | `string(36)` | UUID4, который выдал клиент. |
| `text` | text | Текст заметки, `\n` между строками. |
| `position` | integer | Порядок в колоде; меньше — выше. |
| `created_at` | timestamp | Когда создана на клиенте. |
| `server_updated_at` | timestamp(6) | Серверная метка версии; источник истины для конфликтов. |
| `deleted_at` | timestamp, nullable | Tombstone: NULL — заметка жива. |

Индексы:

- `unique(['user_id', 'client_id'])` — идентичность заметки;
- `index(['user_id', 'server_updated_at'])` — курсорный pull.

`client_id` хранится **строкой в нижнем регистре**, а не типом `uuid`: MySQL
по умолчанию сравнивает строки регистронезависимо, и смешанный регистр дал бы
дубликаты [research 05 §1.1](research/05-laravel-storage.md).

### 3.2 Заметка на клиенте

`notes.json` из [спеки v1 §5.1](../edge-notes/spec.md) расширяется:

```json
{
  "version": 1,
  "notes": [
    {
      "id": "0f0c2f4e-6a1b-4c3d-9e8f-1a2b3c4d5e6f",
      "text": "Groceries\nmilk\neggs\nbread",
      "created": 1793025619.33,
      "updated": 1793025900.12,
      "position": 0,
      "server_updated_at": "2026-11-21T09:12:44.318127Z",
      "synced": true
    }
  ]
}
```

- `position` — число; порядок при чтении собирается сортировкой.
- `server_updated_at` — iso8601 с микросекундами, `null` для никогда не
  отправленной заметки.
- `synced` — `false`, если заметка есть в очереди; UI может показать, что
  изменение не ушло, но по умолчанию не показывает.
- **Миграция при чтении** (спека v1 §5.1): файл без `position` читается как
  есть, порядок берётся из индекса и сразу переписывается в `position`.
  `version` остаётся `1`.

### 3.3 Настройки синхронизации

`sync.json` в каталоге данных, рядом с `notes.json`:

```json
{
  "version": 1,
  "enabled": false,
  "server": "https://notes.example.com",
  "email": "user@example.com",
  "token": "1|8f2c…",
  "cursor": "2026-11-21T09:12:44.318127Z",
  "last_sync": "2026-11-21T09:13:02Z"
}
```

- Файл создаётся при первом включении синхронизации; до этого его нет, и
  сетевые модули не импортируются вовсе.
- Права `0600`, владелец — пользователь. Запись атомарная (см. §7.4).
- `enabled: false` при существующем файле — состояние **паузы**: токен
  сохранён, сеть не используется.
- Отсутствие файла — состояние «синхронизация никогда не настраивалась».

## 4. Протокол

Все эндпоинты живут под `/api/sync`, требуют `Authorization: Bearer <token>`
и отвечают JSON. Ошибки — `4xx`/`5xx` с телом `{"message": "..."}`.

### 4.1 Токены

| Метод | Путь | Аутентификация | Назначение |
|---|---|---|---|
| `POST` | `/api/sync/tokens` | session (веб-вход) | Выдать токен устройства. Тело: `{name}`. Ответ: `{token}`, показывается один раз. |
| `DELETE` | `/api/sync/tokens` | Bearer | Отозвать текущий токен. |

Клиент получает токен так: пользователь вводит email и пароль на странице
Sync, клиент делает `POST /api/sync/tokens` с basic-аутентификацией по этим
данным (Laravel Fortify валидирует), получает `{token}` и сохраняет его.
`plainTextToken` существует только в ответе: на сервере лежит его SHA-256 хеш
[research 05 §2](research/05-laravel-storage.md).

### 4.2 Push: отправка изменений

```
POST /api/sync/changes
```

Тело:

```json
{
  "device": "dev-pc",
  "changes": [
    {
      "id": "0f0c2f4e-…",
      "text": "Groceries\nmilk",
      "created": 1793025619.33,
      "position": 0,
      "base": "2026-11-21T09:12:44.318127Z",
      "deleted": false
    }
  ]
}
```

- `base` — значение `server_updated_at`, которое клиент видел последним;
  для новой заметки — `null`.
- `deleted: true` — tombstone; текст и позиция игнорируются.
- Сервер применяет изменения **в одной транзакции** и отвечает:

```json
{
  "applied": [
    {"id": "0f0c2f4e-…", "server_updated_at": "2026-11-21T09:15:01.002331Z", "deleted": false}
  ],
  "rejected": [
    {"id": "a1b2…", "reason": "stale"}
  ]
}
```

Правило: изменение применяется, если `base` равно текущему
`server_updated_at` или `base` равно `null` и заметки ещё нет. Иначе оно
отклоняется со `reason: "stale"`, и клиент получит актуальную версию при
следующем pull. Это и есть «последняя запись побеждает» по серверному
времени: **сервер всегда ставит `server_updated_at` сам**, значение из
запроса не принимается.

Удаление ставит `deleted_at` и `server_updated_at` **в одном UPDATE**:
`$model->delete()` не бампает `server_updated_at`, и без этого надгробие не
долетит до других машин [research 05 §1.3](research/05-laravel-storage.md).

### 4.3 Pull: получение изменений

```
GET /api/sync/changes?since=<iso8601>&limit=500
```

Ответ:

```json
{
  "changes": [
    {
      "id": "0f0c2f4e-…",
      "text": "Groceries\nmilk",
      "position": 0,
      "created": 1793025619.33,
      "server_updated_at": "2026-11-21T09:15:01.002331Z",
      "deleted": false
    }
  ],
  "cursor": "2026-11-21T09:15:01.002331Z",
  "has_more": false
}
```

- `since` — курсор из `sync.json`; без него отдаётся всё.
- **Tombstones отдаются тоже** — запрос идёт через `withTrashed()`, чтобы
  клиент различал «удалено» и «не получено».
- `limit` по умолчанию 500; `has_more: true` означает, что нужно повторить с
  новым курсором.
- Курсор — `server_updated_at` последней отданной записи; сравнение строго
  `>` (порядок гарантирован монотонностью).

### 4.4 Веб-UI

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/register`, `/login`, `/logout` | Fortify, Blade-вьюхи. |
| `GET` | `/notes` | Список заметок пользователя в порядке `position`. |
| `GET` | `/notes/{client_id}` | Одна заметка; правка через обычную форму `PATCH`. |
| `PATCH` | `/notes/{client_id}` | Сохранение текста; ставит `server_updated_at`. |

Веб-правка — такой же источник изменений, как клиент: она ставит новое
`server_updated_at`, и следующий pull на десктопе её принесёт.

### 4.5 OpenAPI

Контракт — Scramble, экспорт в `api.json` в репозитории сервера
(`php artisan scramble:export --path=api.json --fail-on-unknown`). Публичный
`/docs/api.json` остаётся закрытым гейтом `RestrictedDocsAccess`; источник
истины для клиента — **закоммиченный файл**, чтобы CI клиента мог его читать
без сети [research 05 §4](research/05-laravel-storage.md).

## 5. Разрешение конфликтов

1. Оба устройства правят одну заметку, пока не синхронизированы.
2. Первое успевает отправить — его `server_updated_at` становится новым.
3. Второе отправляет с устаревшим `base` и получает `rejected: stale`.
4. Второе делает pull, получает чужую версию и **заменяет локальную**
   (правило «последняя запись побеждает»); правка второго теряется.

**Потеря правки не показывается.** Это осознанная цена простоты (решение
4.5); конфликтных копий и merge по строкам нет.

### 5.1 Удаление

- Удаление на клиенте кладёт tombstone в очередь.
- Tombstone живёт на сервере **30 дней**
  (`Schedule::command('notes:purge-tombstones')->daily()` в
  `routes/console.php`).
- Устройство, не синхронизировавшееся дольше 30 дней, при первом pull может
  вернуть удалённую заметку. **Известное ограничение**, записано явно.
- Удаление необратимо на сервере: 10-секундный `undo` в клиенте работает
  только до отправки tombstone. Если изменения уже ушли, undo создаёт заметку
  заново с новым `server_updated_at`.

## 6. Клиент

### 6.1 Состояния

| Состояние | Признак | Что происходит |
|---|---|---|
| **Off** | нет `sync.json` или `enabled: false` | Сеть не используется, сетевые модули не импортируются. |
| **Paused** | `enabled: false`, файл есть | То же, но токен сохранён; тумблер включит без ввода пароля. |
| **On** | `enabled: true` | Push по сохранению, pull при старте и периодически. |
| **Needs attention** | `enabled: true`, но последний push вернул `401` | Строка статуса показывает `Signed out · notes not syncing`. |

### 6.2 Цикл

1. Пользователь сохраняет заметку (`store.save`).
2. Изменение попадает в `queue.json` — **до** попытки отправки.
3. Поток отправляет `POST /api/sync/changes`.
4. Ответ `2xx` → применить `server_updated_at`, убрать из очереди.
5. `401` → остановить синхронизацию, перевести в **Needs attention**.
6. Сетевые ошибки → оставить в очереди, повторить с backoff (до 30 с).
7. Pull выполняется при старте, после успешного push и раз в 5 минут.

HTTP — блокирующий `http.client` в фоновом потоке с таймаутом сокета; в
главный цикл возврат через `GLib.idle_add` [research 06 §3](research/06-client-http-queue.md).
Периодический pull — отдельный `GLib.timeout_add_seconds`. Второй экземпляр
`retry.Retrier` держит backoff очереди.

### 6.3 Файлы

| Файл | Назначение | Права |
|---|---|---|
| `notes.json` | заметки | `0644` (как сейчас) |
| `sync.json` | настройки + токен | `0600` |
| `queue.json` | очередь отправки | `0600` |

Все три пишутся атомарно: temp + `fsync` + `os.replace` + `fsync` каталога
(паттерн из `store.py` §5.2). Очередь пишется под `threading.Lock`:
атомарная замена не сериализует двух писателей.

### 6.4 Интерфейс

По решению прототипа 09:

- **Строка-тумблер** в веере, под полем поиска:
  `[тумблер] Sync off · local only` слева, `Set up` справа. Высота 26 px.
  В выключенном состоянии вторая строка — `Turn on to sync with LurkNotes`.
- **Точка статуса** в шапке перед кнопками: серая — Off/Paused, зелёная — On,
  оранжевая — Needs attention.
- **Страница Sync** в панели, открывается по `Set up` и `Ctrl+,`: заголовок,
  тумблер, email и пароль (когда сессии нет), кнопка входа, статус и
  `Last sync`. Колонка табов остаётся слева.
- `Esc` и `»` со страницы Sync возвращают в веер, не закрывая панель заметки.
- **Онбординг** (спека v1 §4.6) получает третью строку про синхронизацию.

Цвета статуса дополняют палитру спеки v1 §6.4:

| Роль | Цвет |
|---|---|
| Sync is on | `#7bb489` |
| Needs attention | `#c98a6b` |

## 7. Сервер

### 7.1 Состав

| Компонент | Пакет / место |
|---|---|
| API-токены | `laravel/sanctum` |
| Веб-вход | `laravel/fortify` + Blade-вьюхи |
| OpenAPI | `dedoc/scramble` |
| Чистка надгробий | команда `notes:purge-tombstones` + `Schedule::daily()` |
| Агентские инструменты | `laravel/boost` (уже установлен) |

### 7.2 Миграции

`notes`:

```php
$table->id();
$table->foreignId('user_id')->constrained()->cascadeOnDelete();
$table->string('client_id', 36);
$table->text('text')->nullable();
$table->integer('position')->default(0);
$table->timestamp('created_at_client')->nullable();
$table->timestamp('server_updated_at', precision: 6)->useCurrent();
$table->softDeletesTz();
$table->unique(['user_id', 'client_id']);
$table->index(['user_id', 'server_updated_at']);
```

`created_at`/`updated_at` Laravel не используются для синхронизации: время
создания заметки приходит с клиента (`created_at_client`), а версия — это
`server_updated_at`.

### 7.3 Применение изменений

Одна транзакция на запрос, `lockForUpdate()` по строке пользователя перед
циклом — так параллельные push'ы одного пользователя не гоняются за
`position` [research 05 §6](research/05-laravel-storage.md). Для каждой
заметки:

1. найти по `(user_id, client_id)`, включая `withTrashed()`;
2. сравнить `base` с текущим `server_updated_at`;
3. при совпадении — обновить, поставить `server_updated_at = now(6)`;
4. при удалении — `deleted_at = now()` и `server_updated_at = now(6)` одним
   обновлением;
5. при несовпадении — в `rejected`.

### 7.4 Валидация

- `id` — `['required', 'uuid:4', 'regex:/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/']`
  (`uuid:4` пропускает верхний регистр, регэксп его запрещает).
- `position` — целое; порядок — суммарное свойство колоды, поэтому при
  перестановке клиент отправляет все сдвинутые заметки разом.

### 7.5 Веб-страницы

Blade, без JS-фронтенда: список заметок, страница заметки с формой, вход и
регистрация. Общая палитра сайта — светлая, тёмная тема сайта вне этой спеки.

## 8. Нефункциональные требования

- **Выключенная синхронизация:** ноль сетевых сокетов — проверка
  `probe_network` в `scripts/acceptance.py` остаётся без изменений.
- **Включённая:** запросы только к `server` из `sync.json`; телеметрии нет.
- **`kill -9`** во время записи очереди или `sync.json` не теряет данные:
  атомарная замена, как в `store.py`.
- **Токен** не пишется в логи и не попадает в сообщения об ошибках.
- **Холодный старт** не ухудшается: сетевые модули импортируются лениво,
  только при включённой синхронизации.

## 9. Ошибки

| Ситуация | Поведение |
|---|---|
| Нет сети | Изменения копятся в очереди, backoff до 30 с, статус остаётся On. |
| `401` от сервера | Синхронизация останавливается, статус Needs attention, `Sign in` на странице Sync. |
| `422` на изменение | Изменение убирается из очереди, пишется в лог; остальные применяются. |
| Сервер недоступен `5xx` | Как «нет сети». |
| `sync.json` битый | Считать синхронизацию выключенной, показать ошибку, файл не перезаписывать. |
| Расхождение версии `notes.json` | Только чтение, как в спеке v1. |

## 10. Критерии готовности

1. Синхронизация выключена — приложение не открывает ни одного сокета.
2. Включение требует email и пароля; после входа появляется токен, а
   строка статуса становится `Sync on`.
3. Правка на машине A появляется на машине B в течение 5 минут или сразу
   после сохранения, если B активен.
4. Правка на сайте появляется на десктопе после pull.
5. Удаление на A удаляет заметку на B и не воскресает.
6. Правка одной заметки на двух машинах без связи оставляет версию,
   пришедшую на сервер последней.
7. `kill -9` во время отправки не теряет изменение из очереди.
8. Отзыв токена на сервере переводит клиент в Needs attention.
9. Публичный `/docs/api.json` закрыт, закоммиченный `api.json` соответствует
   коду (`scramble:export --fail-on-unknown` в CI).

## 11. Открытые вопросы

Решаются при реализации, не блокируют старт:

- **Формат `last_sync`** — человекочитаемый «2 minutes ago» или ISO.
- **Срок жизни токена** — бессрочный до отзыва или с истечением.
- **Поведение при `snap remove`** — предупреждать ли о потере токена.
- **Тёмная тема сайта** — вне этой спеки.
