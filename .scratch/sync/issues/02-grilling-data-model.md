# Grilling: модель данных и порядок

Type: grilling
Status: resolved
Blocked by:

## Question

Зафиксировать, что именно синхронизируется между клиентом и сервером,
как устроена идентичность заметки между машинами и как передаётся порядок
колоды. Проверить определение **Note** в глоссарии против кода.

## Answer

### Что синхронизируется

- **(1.4)** Синхронизируем `id`, `text`, `created`, локальный `updated` и
  порядок. Цвет не синхронизируем: его нет в коде, хотя глоссарий его
  упоминает. Глоссарий надо поправить отдельным тикетом — убрать «цвет» из
  определения Note.

### Идентичность

- **(3.4)** Идентификатор остаётся **UUID4, который генерирует клиент**.
  Считаем коллизию `id` между устройствами статистическим шумом. Составной
  ключ `(device_id, id)` не вводим: он ломает простой merge и требует
  API с двумя ключами.
- Следствие для сервера: `notes.id` — это клиентский UUID, а не
  автоинкремент. Уникальность в пределах пользователя.

### Порядок колоды

- **(3.3)** Порядок — **число `position` на самой заметке**, а не отдельный
  список id на сервере и не локальное состояние. Отдельный список дал бы
  целостность «порядок ровно один», но каждая перестановка — правка всего
  списка, а merge по «последняя запись» на таком объекте почти всегда
  теряет чужие перестановки.
- Следствие для клиента: `notes.json` получает поле `position`, а порядок
  при чтении собирается сортировкой по нему. Текущая схема хранит порядок
  как индекс в массиве, поэтому это **изменение формата файла**: нужна
  миграция при чтении старых файлов (отсутствие `position` — присвоить по
  индексу) и решение, поднимать ли `version`.

### Что это меняет в спецификации v1

- §5.1 «формат `notes.json`» расширяется полем `position`; версия файла
  остаётся 1, если миграция при чтении достаточна. Если формат меняется
  несовместимо — версию поднять и описать путь чтения старых файлов.
