# Grilling: цель и границы

Type: grilling
Status: resolved
Blocked by:

## Question

Зафиксировать, что значит «готово» для этой карты: что должно быть правдой
к её концу, чтобы её закрыли и передали в реализацию. Заодно решить, что
представляет собой `web/` (новый бэкенд с нуля или пристройка к существующему
сайту), где живёт код и где — контракт API.

## Answer

### Цель и её границы

- **(1.1)** Цель карты — **спека**, а не работающая фича. Синхронизация
  состоит из решений (идентичность, конфликты, удаление, доступ), и их
  нужно зафиксировать до кода.
- **(2.1)** `web/` — **новый бэкенд с нуля**: чистый Laravel 13 с одним
  `User` и маршрутом `welcome`. Сайту нужен собственный бэкенд вместе с
  веб-интерфейсом; веб-UI входит в объём.
- **(3.2)** `web/` живёт в **отдельном репозитории**: сервер в
  GitLab `hoter/lurknotes`, клиент — GitHub `hoter/lurknotes`. Оба сегодня
  называются `lurknotes`; в текстах различать «клиент» и «сервер».
- **(3.1)** Десктопный код (Python, упаковка, спеки, карты) остаётся в
  репозитории клиента. В отдельный репозиторий уезжают только сервер,
  миграции, API и веб-UI.
- **(3.4)** Переезд `web/` — **предусловие, закрытое владельцем**: git в
  `web/` уже инициализирован и запушен в GitLab, 60 файлов в истории.
- **(2.2)** Контракт API — **OpenAPI в репозитории сервера как источник
  правды**, опубликованный по URL; клиент проверяет свои модели против
  него в CI.
- **(2.3)** Эта карта покрывает **обе стороны**; тикеты реализации живут
  там, где живёт код. Если серверный репозиторий окажется переименован,
  ссылки в карте надо поправить.

### Следствия, записанные явно

- Спека v1 утверждает «без сети, аккаунтов и синхронизации» (§1) и
  исключает синхронизацию (§2). Синхронизация меняет эту границу; спека v1
  правится ссылкой на эту карту отдельным тикетом, а не переписывается.
- Хостинг и домен — не решение о синхронизации; допущение: сайт публичный,
  TLS и почта будут, провайдер выбирается при реализации.
